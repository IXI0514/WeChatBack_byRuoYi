# 12 · 服务器增量更新操作说明

适用：已有服务正常部署，源码已在 Gitee，服务器目录为 `/home/ubuntu/mywebshow`。使用现有 ubuntu 账号，在服务器 Docker 内构建，不在本地上传 JAR/dist。

增量更新保留 MySQL、Redis、上传文件、证书和生产配置，不是重置部署。本文不强制增加备份步骤；未备份时，误执行破坏性 SQL 可能无法恢复。重置清空数据请另见 [13 · 重置部署](./服务器Docker重置与重新部署.md)，日常更新不要执行其中的清理命令。

已使用 `/home/ubuntu/quickdeploy` 分步脚本完成首次部署时，可直接执行：

```bash
bash /home/ubuntu/quickdeploy/reset-deploy.sh update
```

该命令实现本文第 2、3、4、6、7 节中的代码发布、应用构建/替换、Nginx 重载和验收；不会自动执行数据库 SQL。数据库变更仍必须先按第 5 节人工核对并执行，再运行 `update`。

## 1. 更新原则与顺序

本地修改并验证 → 提交/推送 Gitee → 服务器检查并拉取 → 核对新增配置与增量 SQL → 构建镜像 → 按需执行 SQL → 替换应用容器 → 刷新 Nginx 上游 → 验收。

- 不删除 `ruoyi-deploy/data/`，不执行 `docker compose down -v`、全局 Docker 清理或重新初始化数据库。
- 不覆盖已有 `.env`，只补充新版要求的变量；不随意修改 MySQL/Redis 密码。
- 不执行全量建库 SQL。把增量 SQL 放入 `mysql/init/` 不会让已有数据库自动执行。
- `restart` 不重新打包代码，也不更新容器环境变量；代码修改需 build + up，环境变量修改需重建容器。
- 本文使用 `sudo docker compose`，避免 ubuntu 尚未取得 Docker 权限的问题。Git 使用 ubuntu 自身执行，不加 sudo。
- 单实例更新会有短暂中断；本文不是零停机发布方案。

## 2. 拉取前检查

本地先提交并推送本次代码、部署配置和 SQL；不要提交密码、证书、数据或编译产物。

服务器执行：

```bash
cd /home/ubuntu/mywebshow
pwd
git status --short
git remote -v
git branch --show-current
git rev-parse --short HEAD
cd ruoyi-deploy
sudo docker compose ps -a
sudo docker compose config --quiet && echo "Compose 配置有效"
df -h .
```

确认 remote 是自己的 Gitee 仓库，当前分支是准备发布的分支，并记录旧提交号。若工作区有修改，先确认是否为服务器配置；不要强制覆盖或直接 reset。现有后端若已处于 Restarting，应先检查错误日志。

`config --quiet` 成功时不打印正文，后面的提示表示返回码为 0。它只验证配置，不能证明服务能正常运行。不要直接打印完整 Compose 配置到聊天中，可能包含密码。

## 3. 拉取代码并确定更新范围

在同一个 SSH 终端执行：

```bash
cd /home/ubuntu/mywebshow
previous_commit=$(git rev-parse HEAD)
git pull --ff-only
```

仅在 pull 成功后继续：

```bash
git rev-parse --short HEAD
git diff --name-status "$previous_commit" HEAD
git status --short
cd ruoyi-deploy
sudo docker compose config --quiet && echo "Compose 配置有效"
```

如果提示分支分叉或本地修改冲突，停止发布，先处理；不要强制拉取。对照新版 `.env.example`，用 `nano .env` 补齐新变量，不要整份复制覆盖。

| 改动范围 | 需要操作 |
| --- | --- |
| Java、Mapper、后端 application 配置、后端 Dockerfile | 构建并替换 ruoyi-admin |
| Vue、前端接口封装、前端构建配置 | 构建并替换 ruoyi-ui |
| 数据库结构、菜单、初始化数据调整 | 人工核对并执行本次所需增量 SQL |
| .env、Compose 中应用环境变量 | 重建受影响应用容器，单纯 restart 不生效 |
| nginx/nginx.conf、HTTPS 证书 | 确认挂载有效，nginx -t 成功后 reload |
| site 静态文件 | 挂载目录直接生效，通常无需构建或重启 |
| 仅 Markdown 文档 | 无需发布容器 |

本次小程序凭证功能若尚未上线：补充 `MINIAPP_API_AES_KEY`，后台 `miniapp.valid.ids` 配置允许的小程序标识，前后端使用一致密钥。只改 token 从 header 到查询参数无需数据库迁移，需更新后端及小程序调用代码。详情见 [22 · 小程序接口](./小程序接口/接口说明.md)。

## 4. 先构建，不急于停旧服务

前后端都更新：

```bash
cd /home/ubuntu/mywebshow/ruoyi-deploy
sudo docker compose build ruoyi-admin ruoyi-ui
```

仅后端则执行 `sudo docker compose build ruoyi-admin`；仅前端执行 `sudo docker compose build ruoyi-ui`。构建失败立即停止，旧运行容器不会仅因 build 而被替换。检查构建输出中的依赖下载、编译错误及磁盘空间，不要继续发布。

无需每次 pull MySQL/Redis 镜像，不要把基础服务版本升级混入普通应用更新。

## 5. 有数据库变更才执行本节

没有新增数据库变更时跳过。仅执行本次尚未应用且已核对的脚本，不要批量执行 docs/sql 下所有文件。当前项目没有自动迁移版本记录，需自行记录发布提交、脚本名、执行时间和结果。

例如首次为已有库增加中继台表及菜单，核对：

```bash
cd /home/ubuntu/mywebshow/ruoyi-deploy
less ../ruoyi-source/docs/sql/6-中继台管理增量.sql
```

该脚本使用存在性判断，但不能替代将来对已有列的 ALTER 迁移；还应确认菜单 ID 没被其他自定义菜单占用。基础脚本 1～4 不是日常更新脚本；组织清理脚本 5 仅在确实需要该业务调整时单独执行。

为避免旧应用在迁移时继续写入，确认构建成功后，安排短维护窗口：

```bash
sudo docker compose stop ruoyi-admin
sudo docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot "${MYSQL_DATABASE:-ry}"' < ../ruoyi-source/docs/sql/6-中继台管理增量.sql
```

第二条命令返回码必须为 0，且输出中不能有 SQL 错误。可紧接执行 `echo "sql_exit_code=$?"` 检查。密码取自容器环境变量，不使用 grep 解析 .env；不要把密码输出到日志。如果数据库实际密码与容器环境值已不同，会认证失败，应先修复配置一致性，不要重建数据库。

验证表与菜单：

```bash
sudo docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot "${MYSQL_DATABASE:-ry}" -e "SHOW TABLES LIKE '\''miniapp_repeater'\''; SELECT menu_id,menu_name,perms FROM sys_menu WHERE perms LIKE '\''miniapp:repeater:%'\'';"'
```

SQL 失败立即停止，不要继续更新应用。MySQL DDL 可能已经部分提交，不要以为失败会自动全量回滚；根据实际结果修复，再决定恢复旧应用还是继续。菜单执行成功后，普通角色还需在后台授权并重新登录。

## 6. 替换应用容器

构建及所需 SQL 均成功后，前后端都更新执行：

```bash
cd /home/ubuntu/mywebshow/ruoyi-deploy
sudo docker compose up -d --no-deps --force-recreate ruoyi-admin ruoyi-ui
sudo docker compose ps -a
sudo docker compose logs --since=5m --tail=150 ruoyi-admin ruoyi-ui
```

仅更新一个服务，就只在 up 命令中写对应服务名。`--no-deps` 避免此次应用更新连带操作 MySQL/Redis，前提是依赖已运行正常。`--force-recreate` 确保环境变量也按当前配置更新。

应看到后端启动成功且没有连续异常，不是只看到 Started 就结束。等待一会儿再次执行 `sudo docker compose ps -a`，确认没有 Restarting/Exited。只改后端环境变量可跳过 build，但仍需重建后端。

### 刷新 Nginx 上游地址

当前 Nginx 配置的 upstream 使用容器服务名；应用容器替换后 IP 可能变化，因此在应用启动成功后执行：

```bash
sudo docker compose exec nginx nginx -t
```

只有测试成功才执行：

```bash
sudo docker compose exec nginx nginx -s reload
```

若 nginx 正在重启，exec 无法使用，先查看 `sudo docker compose logs --tail=100 nginx`。修复证书、配置或上游启动问题后，再启动/重建 nginx；不要反复忽略错误。单文件挂载的 nginx.conf 如果被编辑器替换为新文件，容器可能仍看到旧文件，此时按需 `sudo docker compose up -d --no-deps --force-recreate nginx` 后再验证。

## 7. 验收

检查数据库实际查询和 Redis 身份验证，不只看 healthy：

```bash
sudo docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot "${MYSQL_DATABASE:-ry}" -e "SELECT 1;"'
sudo docker compose exec -T redis sh -c 'REDISCLI_AUTH="$REDIS_PASSWORD" redis-cli ping'
```

分别应返回 1 和 PONG。不要使用 `mysqladmin ping` 代替数据库密码有效性验证。

检查域名、页面、后端入口：

```bash
curl -I --max-time 15 https://73ham.top/
curl -I --max-time 15 https://73ham.top/admin/
curl -i --max-time 15 https://73ham.top/api/repeater/list
```

- 首页和后台入口正常返回 200；浏览器访问后台并实际登录、打开本次修改页面验证。
- 未传 token 的 list，在密钥正确配置时预期为 401 JSON，不是 502。503 表示密钥配置有问题。
- 401 只能证明拒绝未认证请求，还需按接口说明生成 token，携带 `data: { token }` 调用并确认 200 和实际中继台数据。
- 新增、编辑等业务操作仅用测试数据验收；普通角色需核对菜单与按钮权限。
- HTTPS 验证不要加 `-k` 绕过证书问题。
- token 位于 URL，当前 Nginx 日志格式包含完整请求；生产应另行脱敏，分享日志前务必去除 token。

## 8. 出错时如何处理

| 现象 | 处理 |
| --- | --- |
| 拉取/构建失败 | 停止发布，旧容器保持运行，先处理具体错误 |
| 后端 Restarting | 查后端日志，重点检查 JDBC、Redis、环境变量和 SQL 是否匹配 |
| 页面或接口 502 | 检查后端/UI 是否真正启动，再检查 Nginx 上游并 reload |
| 新代码未生效 | 核对提交号，确认 build 成功且执行了 up 重建，不是只 restart |
| MySQL/Redis 密码错误 | 核对运行配置与实际密码，禁止通过清空数据解决 |
| SQL 部分失败 | 停止后续操作，检查已执行结果，不能盲目重复或假定已回滚 |

记录发布前后提交号及本次 SQL。需要恢复旧代码时，应先确认旧代码兼容变更后的数据库，再使用已确认的旧版本重建应用。没有备份时，代码回退不能恢复删除的数据；本流程不承诺数据库自动回滚。

## 9. 无 SQL、无环境配置变更时的快捷流程

仅在已确认 Git 工作区干净、依赖正常且本次不涉及迁移/配置后使用。每一步成功后再执行下一步：

```bash
cd /home/ubuntu/mywebshow
git pull --ff-only
cd ruoyi-deploy
sudo docker compose config --quiet
sudo docker compose build ruoyi-admin ruoyi-ui
sudo docker compose up -d --no-deps --force-recreate ruoyi-admin ruoyi-ui
sudo docker compose logs --since=5m --tail=100 ruoyi-admin
```

确认应用启动后：

```bash
sudo docker compose exec nginx nginx -t && sudo docker compose exec nginx nginx -s reload
sudo docker compose ps -a
curl -I --max-time 15 https://73ham.top/admin/
```

不要将整段当成失败也继续的一键脚本。数据库和生产配置有变更时，必须回到前面分步流程。
