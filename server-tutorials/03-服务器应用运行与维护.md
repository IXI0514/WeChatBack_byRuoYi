# 44 · 第 3 篇：服务器应用运行与维护

> 前置：完成[第 1 篇](./01-Nginx入门与实践.md)的静态网站与模拟 `/api/`。  
> 目标：不涉及后台业务开发，专门学习一个后台程序交付到服务器后，如何安全、稳定、可回滚地运行。

真实后台可能由 Java、Node.js、Python、Go 或其他语言开发，但服务器管理员面对的核心问题相同：启动命令是什么、监听哪个地址、配置放在哪里、失败如何重启、日志去哪里、怎样升级和回滚。

---

## 3.1 把“程序”变成“服务”

手工在 SSH 中运行程序只适合短暂测试：终端断开后它可能退出，服务器重启后也不会自动恢复。一个可维护的服务至少要有：

- 明确的运行用户；
- 固定的工作目录和启动命令；
- 只监听必要的 IP 与端口；
- 开机自启和失败重启；
- 可查询的状态与日志；
- 健康检查；
- 可重复的发布与回滚方法。

在 Ubuntu 上常见的两种管理方式：

| 方式 | 适合 | 第一阶段建议 |
| --- | --- | --- |
| systemd 直接运行程序 | 单个服务、希望先理解 Linux 原理 | 先学，会直接看到进程、权限、日志和端口 |
| Docker Compose | 多服务、依赖复杂、团队已有镜像交付 | 掌握 systemd/Nginx 后再学第 2 篇 |

不要同时让宿主机 Nginx 和 Nginx 容器抢占 80/443。课程主线始终由宿主机 Nginx 作为公网入口。

## 3.2 【推荐】规划目录、用户和端口

以下是一种清晰的布局：

```text
/opt/my-api/                 # 程序版本，发布时更新
├── releases/
│   ├── 20260907-120000/
│   └── 20260908-093000/
└── current -> releases/20260908-093000

/etc/my-api/my-api.env      # 环境配置与敏感信息
/var/lib/my-api/            # 持久化运行数据（如果应用需要）
/var/log/my-api/            # 应用自行写文件日志时使用
```

代码、配置、数据和日志分离，升级程序时才不会误删数据或把密码打进发布包。

创建不能直接登录的专用服务用户：

```bash
sudo useradd --system --home /nonexistent --shell /usr/sbin/nologin my-api
sudo install -d -o my-api -g my-api -m 0750 /var/lib/my-api
sudo install -d -o my-api -g my-api -m 0750 /var/log/my-api
sudo install -d -o root -g my-api -m 0750 /etc/my-api
```

命令拆解：

- `useradd --system`：创建系统服务账号，而不是普通人员账号；
- `--home /nonexistent`：声明该账号没有实际主目录；
- `--shell /usr/sbin/nologin`：禁止用这个账号建立交互式登录；
- `install -d`：创建目录；`-o` 指定所有者，`-g` 指定组，`-m` 直接设置权限；
- `0750`：所有者可读写进入、同组用户可读进入、其他用户无权访问。

这里的 `my-api` 是服务账号，不应加入 `sudo` 组，也不需要设置登录密码。

端口约定：

- Nginx 对公网监听 80/443；
- 应用监听 `127.0.0.1:8080`；
- 安全组和 UFW 不开放 8080；
- 数据库等内部依赖也不直接暴露公网。

如果后台程序只支持监听 `0.0.0.0`，仍不要在安全组开放它的端口，并应尽量通过应用参数或配置改成回环地址。

## 3.3 【推荐】配置与敏感信息

不要把数据库密码、令牌、私钥写进 Git 仓库、构建产物或 systemd 服务文件。可以使用仅 root 与服务组可读的环境文件：

```bash
sudo nano /etc/my-api/my-api.env
sudo chown root:my-api /etc/my-api/my-api.env
sudo chmod 640 /etc/my-api/my-api.env
```

`chown root:my-api` 把所有者设为 root、所属组设为 `my-api`；`640` 表示 root 可读写、服务组只读、其他用户无权限。这样服务能读取配置，但不能自行修改它。

示意内容：

```text
APP_ENV=production
LISTEN_HOST=127.0.0.1
LISTEN_PORT=8080
DATABASE_URL=请替换为真实连接信息
```

注意事项：

- 是否支持这些变量以及变量名是什么，必须以后台程序的交付说明为准；
- 环境变量不是加密保险箱，同机 root 和某些进程检查手段仍可能看到；
- 不要在终端命令行直接附带敏感值，以免进入 shell 历史；
- 定期轮换凭据，备份时也要保护配置文件。

## 3.4 【必做：非容器服务】用 systemd 管理后台程序

第 1 篇的 `mock-api.service` 已展示最小服务。替换真实程序时，向开发或交付人员确认以下信息：

1. 完整启动命令；
2. 运行时版本与依赖；
3. 工作目录；
4. 健康检查 URL；
5. 如何优雅停止；
6. 配置与数据目录；
7. 正常启动需要多久。

下面是通用骨架，**【示例】不可不加修改地直接使用**：

```ini
[Unit]
Description=My API service
After=network.target

[Service]
Type=simple
User=my-api
Group=my-api
WorkingDirectory=/opt/my-api/current
EnvironmentFile=/etc/my-api/my-api.env
ExecStart=/opt/my-api/current/bin/start
Restart=on-failure
RestartSec=5
TimeoutStopSec=30
KillSignal=SIGTERM

# 确认应用兼容后再逐项启用安全限制
NoNewPrivileges=true
PrivateTmp=true
ProtectHome=true

[Install]
WantedBy=multi-user.target
```

主要指令：

| 指令 | 含义 |
| --- | --- |
| `After=network.target` | 在基础网络单元之后启动；它不保证外部网络服务已经可用 |
| `Type=simple` | `ExecStart` 启动的进程就是需要持续跟踪的主进程 |
| `User` / `Group` | 以哪个低权限身份运行 |
| `WorkingDirectory` | 启动前切换到哪个目录；不存在会出现 `200/CHDIR` |
| `EnvironmentFile` | 从指定文件读取环境变量；文件不存在通常会导致启动失败 |
| `ExecStart` | 完整启动命令；第一个路径必须存在且可执行 |
| `Restart=on-failure` | 非正常退出时重启，正常停止时不循环拉起 |
| `RestartSec=5` | 失败后等待 5 秒再重启，避免无间隔循环 |
| `TimeoutStopSec=30` | 最多等待 30 秒让程序正常退出 |
| `KillSignal=SIGTERM` | 停止时先发送可供程序优雅处理的终止信号 |
| `WantedBy=multi-user.target` | enable 后挂入常规多用户启动目标 |

`NoNewPrivileges`、`PrivateTmp` 和 `ProtectHome` 是安全加固项：分别阻止进程获取额外权限、提供隔离的临时目录、限制访问用户主目录。应用需要访问相关资源时可能不兼容，所以应逐项启用并验证。

保存为 `/etc/systemd/system/my-api.service` 后：

```bash
sudo systemd-analyze verify /etc/systemd/system/my-api.service
sudo systemctl daemon-reload
sudo systemctl enable --now my-api
systemctl status my-api --no-pager
journalctl -u my-api -n 100 --no-pager
```

`systemd-analyze verify 文件` 只检查单元文件及其依赖/路径问题；`daemon-reload` 让 systemd 重新读取文件；`enable --now` 同时完成开机启用和立即启动。参数含义与第 0 篇的 systemctl 表一致。

**【验证结果】**

| 检查 | 正常结果 | 异常时先做什么 |
| --- | --- | --- |
| `systemd-analyze verify` | 没有错误输出 | 按提示修正指令名、路径或语法 |
| `systemctl status my-api` | `Active: active (running)` 且存在 `Main PID` | 查看状态底部和 journal |
| `systemctl is-enabled my-api` | `enabled` | 需要开机自启时执行 `systemctl enable my-api` |
| `journalctl -u my-api` | 有正常启动记录，无持续重复错误 | 找到最早出现的根因错误 |

`active (running)` 只证明进程当前存在，不能证明 HTTP、数据库等功能一定正常，所以还要执行下一节的健康检查。

每次修改 `.service` 文件后都需要 `daemon-reload`；只替换程序文件或环境配置通常只需重启服务：

```bash
sudo systemctl restart my-api
```

`Restart=on-failure` 适合大多数长期服务。它能处理意外退出，但不能修复配置错误；如果服务不断重启，第一动作是看日志，而不是提高重试频率。

## 3.5 【必做】健康检查不是“进程还在”

进程存在不代表服务可用。最少分三层检查：

```bash
# 1. 进程层
systemctl is-active my-api

# 2. 后台本机 HTTP 层
curl --fail --silent --show-error http://127.0.0.1:8080/health

# 3. 用户入口层
curl --fail --silent --show-error https://example.com/api/health
```

三条命令都应以退出码 0 结束。紧接着执行 `echo $?` 可以查看上一条命令的退出码：`0` 表示成功，非 0 表示失败。`curl --fail` 遇到 4xx/5xx 会返回失败，`--show-error` 会保留错误信息。

| 哪一层失败 | 主要方向 |
| --- | --- |
| `is-active` 失败 | 进程未运行，查看 systemd 状态与 journal |
| 本机 8080 失败 | 应用未监听、启动未完成或健康路径错误 |
| 本机成功但公网 URL 失败 | Nginx、TLS、DNS、安全组或外层网络 |

理想的健康接口应快速返回 2xx，并只做轻量检查。是否检查数据库、缓存等依赖，需要由开发与运维共同约定；检查过重会让健康检查本身造成负载。

对于定时监控，至少关注：

- 域名是否能解析；
- TLS 证书是否临近到期；
- 首页和 API 健康地址是否返回成功；
- 磁盘、内存、CPU 与系统负载；
- 服务是否在反复重启；
- 备份是否成功以及能否恢复。

## 3.6 【推荐】可回滚的发布流程

“把新文件覆盖到旧目录再重启”很难回滚，也可能留下新旧文件混合状态。更稳妥的流程是每次创建独立版本目录。

以版本 `20260908-093000` 为例：

```bash
sudo install -d -o my-api -g my-api -m 0750 /opt/my-api/releases/20260908-093000
```

把完整发布包上传并解压到该目录，然后在切换前完成：

- 校验文件或压缩包哈希；
- 确认属主和执行权限；
- 检查配置兼容性；
- 运行交付方提供的离线自检；
- 如果涉及数据库变更，先确认它是否可以回滚。

切换软链接时先创建新链接，再在同一文件系统内替换：

```bash
cd /opt/my-api
sudo ln -s releases/20260908-093000 current.next
sudo mv -Tf current.next current
sudo systemctl restart my-api
```

- `ln -s releases/20260908-093000 current.next`：创建一个临时软链接，不复制整份程序；
- `mv -T`：把目标 `current` 当作一个链接/文件处理，而不是进入同名目录；
- `-f`：允许替换已有的 `current` 链接；
- 在同一文件系统内用 `mv` 替换链接通常是瞬时切换，用户不会看到“链接不存在”的中间状态。

**【谨慎】** 执行前先用 `readlink -f current` 记录当前版本，并确认 `current` 本身是软链接。如果它是普通目录，先设计迁移步骤，不要直接套用替换命令。

`readlink -f current` 会解析软链接链并打印最终目标的绝对路径，只读、不修改链接。

立刻验证：

```bash
systemctl status my-api --no-pager
curl --fail http://127.0.0.1:8080/health
curl --fail https://example.com/api/health
```

只有服务状态为 `active (running)`、两层健康检查都成功且日志无新增严重错误，才算发布完成。不要只以 `systemctl restart` 命令没有报错作为成功标准。

失败时让 `current` 指回上一版本并重启。不要在没有备份和回滚方案时执行不可逆数据库升级；程序文件回滚不等于数据库自动回滚。

发布前后记录版本号、时间、操作人、配置变化和验证结果。遇到故障时，这些记录比回忆可靠。

## 3.7 【推荐】日志：先集中，再控制大小

如果应用把日志输出到标准输出/错误，systemd 会交给 journal：

```bash
journalctl -u my-api -n 100 --no-pager
journalctl -u my-api -f
journalctl -u my-api --since '30 minutes ago'
```

`-f` 表示持续跟随新日志；`--since '30 minutes ago'` 只查询最近 30 分钟。按 `Ctrl+C` 结束跟随不会停止后台服务。

Nginx 日志：

```bash
sudo tail -n 100 /var/log/nginx/access.log
sudo tail -n 100 /var/log/nginx/error.log
```

日志至少应帮助回答：请求何时到达、请求路径、状态码、处理耗时、错误类型、服务版本。不要记录密码、访问令牌、完整身份证号等敏感信息。

检查 journal 占用：

```bash
journalctl --disk-usage
```

`--disk-usage` 只统计 journal 日志占用，不执行清理。

Ubuntu 通常会通过 journald 与 logrotate 控制系统和 Nginx 日志。应用若自行写文件日志，也必须配置轮转；不要用定时 `rm` 粗暴删除正在写入的日志文件。

## 3.8 【必做：存在业务数据时】备份与恢复

备份对象按重要性区分：

| 对象 | 是否必须备份 | 说明 |
| --- | --- | --- |
| Git 中的源码 | 通常已有远端版本库 | 仍要确认远端可用 |
| 可重新构建的静态文件/程序包 | 建议保留最近发布版本 | 用于快速回滚 |
| `/etc/nginx/` 和应用配置 | 必须 | 包含运行所需配置，注意保护秘密 |
| 数据库和上传文件 | 必须且最关键 | 需要应用一致性的备份方法 |
| 日志 | 按审计与排障需求 | 设定保留期限，避免撑满磁盘 |

遵循 3-2-1 思路：至少 3 份副本、2 种介质、1 份异地。只有实际恢复过的备份才算可靠。

改 Nginx 配置前可以创建带日期的备份：

```bash
sudo cp -a /etc/nginx/sites-available/mysite /etc/nginx/sites-available/mysite.bak-20260908
```

`cp -a` 的 `a` 是 archive，复制内容并尽量保留权限、时间和软链接属性。备份名带日期便于辨认，但多次在同一天修改时还应加入时间或版本号，避免覆盖已有备份。

数据库备份不能简单复制正在运行的数据目录。应使用数据库官方的逻辑备份、快照或一致性备份工具，并定期在隔离环境演练恢复。

## 3.9 【推荐】容量、安全更新与日常巡检

每周或每次发布前后做一次基础巡检：

```bash
uptime
free -h
df -h
df -ih
systemctl --failed
sudo ss -lntp
sudo nginx -t
sudo certbot certificates
```

系统更新先查看再执行：

```bash
sudo apt update
apt list --upgradable
sudo apt upgrade
```

内核或关键库更新可能需要重启。先安排维护时间、确认服务开机自启和回滚方案，再重启并完成网站与 API 验证。

安全检查重点：

- SSH 是否只允许必要账号，优先使用密钥；
- 22 是否可以限制来源 IP；
- 公网监听是否只有预期端口；
- 后台是否绑定 127.0.0.1；
- 配置文件权限是否过宽；
- 依赖和基础镜像是否仍受支持；
- TLS 续期是否正常；
- 是否存在长期无人维护的测试服务。

## 3.10 【按需选学】同域名接口的几个后续知识点

### 同源与 CORS

网页和 API 都使用 `https://example.com` 时，它们具有相同的协议、主机和端口，浏览器通常不需要跨域 CORS 配置。若以后把 API 改为 `https://api.example.com`，主机不同，就需要由后台准确配置允许的来源。

不要用 `Access-Control-Allow-Origin: *` 加凭据来“解决所有跨域问题”；这既可能无效，也会扩大数据暴露风险。

### 【可选】上传大小和超时

接口上传大文件时，可能需要在对应 `server` 或 `location` 调整：

```nginx
client_max_body_size 20m;
proxy_connect_timeout 5s;
proxy_read_timeout 60s;
```

数值应来自实际需求。无限增大超时和上传限制会增加资源被占用的风险。

### 【可选】WebSocket

真实服务使用 WebSocket 时，需要额外转发升级请求头。普通 REST API 不需要提前添加。按后台框架和 Nginx 官方 WebSocket 文档配置，不要把与当前业务无关的片段全部复制进站点。

### 客户端真实 IP

第 1 篇转发了 `X-Real-IP` 和 `X-Forwarded-For`。后台只有在确认请求确实经过受信任代理时才应信任这些头；如果应用端口暴露公网，客户端可以自己伪造它们。这也是后台端口只监听回环地址的重要原因。

## 3.11 故障处理卡片

收到“网站打不开”时按顺序记录证据：

1. 故障开始时间、影响的域名和路径；
2. `curl` 返回的状态码和错误；
3. Nginx、后台服务状态与最近日志；
4. 80、443、8080 的监听地址；
5. DNS 解析与证书状态；
6. 最近一次发布、配置或系统变更；
7. 回滚后的验证结果。

常见状态码：

| 状态 | 含义方向 |
| --- | --- |
| 301/308 | 重定向，检查 `Location` 是否正确 |
| 403 | 权限或访问规则 |
| 404 | Nginx 路径、静态文件或后台路由不存在 |
| 413 | 请求体超过 `client_max_body_size` |
| 502 | Nginx 无法从后台得到有效响应 |
| 504 | 后台在超时时间内没有响应 |

先恢复服务，再保留日志和时间线分析根因。不要在事故中同时修改多个未知因素，否则很难判断哪项变更有效。
