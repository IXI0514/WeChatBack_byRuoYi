# 41 · 第 0 篇：服务器基础与安全起步

> 目标：能安全登录 Ubuntu 服务器，理解目录、权限、进程、端口和防火墙，并具备最基本的排障能力。  
> 环境：腾讯云 CVM / Ubuntu 22.04 LTS。其他云平台可以照做，但安全组入口名称可能不同。

完成本篇后再进入 [第 1 篇](./01-Nginx入门与实践.md)。不要急着安装 Nginx；先理解下面这张图。

```text
你的电脑 ──SSH/22──▶ 云安全组 ──▶ UFW ──▶ Ubuntu 服务器
浏览器   ──80/443─▶ 云安全组 ──▶ UFW ──▶ Nginx
```

云安全组是云平台外层防火墙，UFW 是服务器内部防火墙。任何一层拒绝，请求都到不了程序。

## 0.1 登录服务器：SSH

SSH 是加密的远程终端协议。服务器没有接在你面前的显示器和键盘，你通常通过 SSH 操作它。

### 【可选】先用控制台登录一次

腾讯云控制台中找到 CVM 实例，使用“登录”或 WebShell。它适合首次检查以及 SSH 失联时救援。

登录后确认系统和当前身份：

```bash
whoami
hostname
cat /etc/os-release
ip -brief address
```

`ip address` 查看网卡地址，`-brief` 将每张网卡压缩为一行。常见的 `lo` 是本机回环网卡，`UP` 表示网卡已启用；云服务器内看到的地址可能是私网 IP，公网 IP 仍以云控制台为准。

### 从自己的电脑登录

在本机 PowerShell、Terminal 或 Linux 终端执行：

```bash
ssh root@服务器公网IP
```

腾讯云镜像常见初始用户是 `root`，但部分云镜像可能使用 `ubuntu` 等用户。以创建实例时显示的登录说明为准。

第一次连接时会显示服务器指纹。应先在云控制台核对实例 IP，再输入 `yes`。这不是普通的确认弹窗：如果一台从未重装的服务器突然提示指纹改变，应先排查原因。

常见错误：

| 现象 | 常见原因 | 先检查什么 |
| --- | --- | --- |
| `Connection timed out` | IP 错误、安全组未开放 22、服务器关机 | 实例状态、公网 IP、安全组 |
| `Connection refused` | SSH 服务未运行或端口已修改 | 用 WebShell 执行 `systemctl status ssh` |
| `Permission denied` | 用户名、密码或密钥不正确 | 登录用户、认证方式、公钥 |
| `Host key verification failed` | 本机记录的指纹与服务器不一致 | 确认是否重装或更换了目标，切勿直接忽略 |

### 【推荐】建立日常管理用户

长期直接使用 root 风险很高。先创建普通用户 `deploy`：

```bash
adduser deploy
usermod -aG sudo deploy
id deploy
```

命令拆解：

- `adduser deploy`：以交互方式创建用户、主目录并设置密码；
- `usermod`：修改现有用户；
- `-G sudo`：把 `sudo` 设为附加用户组；
- `-a`：append，追加而不是替换原有附加组。这里必须和 `-G` 一起使用，否则可能误删该用户原有组；
- `id deploy`：只读验证，输出用户 ID、主组和附加组；结果中应包含 `sudo`。

保持当前 root 会话不要退出，另开一个终端测试：

```bash
ssh deploy@服务器公网IP
sudo whoami
```

最后一条应输出 `root`。只有新会话确认成功，才继续修改 SSH 策略。

### 【推荐】配置密钥登录

在自己的电脑生成密钥，不是在服务器上生成：

```bash
ssh-keygen -t ed25519 -C "server-admin"
```

`ssh-keygen` 用来生成密钥对；`-t ed25519` 指定密钥算法，`-C` 添加便于识别的备注。生成的私钥留在自己的电脑，`.pub` 公钥才可以放到服务器。

macOS/Linux 通常可以执行：

```bash
ssh-copy-id deploy@服务器公网IP
```

Windows 没有 `ssh-copy-id` 时，可以在服务器为 `deploy` 创建 `~/.ssh/authorized_keys`，将本机 `.pub` 公钥的一整行追加进去，并设置权限：

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

`chmod` 修改权限：`700` 表示只有文件所有者能读、写、进入 `.ssh` 目录；`600` 表示只有所有者能读写 `authorized_keys`。SSH 会拒绝使用权限过宽的密钥目录或文件。

**【可选・谨慎】** 确认密钥能在新终端登录后，才考虑禁用 root 和密码登录。Ubuntu 支持在 `/etc/ssh/sshd_config.d/` 放独立配置，便于回退：

```bash
sudo nano /etc/ssh/sshd_config.d/99-hardening.conf
```

```text
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
```

应用前一定先检查，再重载：

```bash
sudo sshd -t
sudo systemctl reload ssh
```

> 保留当前 SSH 会话，另开窗口验证密钥登录。验证失败时可用旧会话撤销配置。不要在密钥尚未验证时禁用密码登录。

## 0.2 命令行的三个基本概念

### 当前用户、当前目录、命令权限

```bash
whoami       # 当前用户
pwd          # 当前目录
ls -la       # 当前目录内容，包括隐藏文件
```

- 普通命令以当前用户权限运行。
- `sudo 命令` 只让这一条命令临时获得管理员权限。
- `~` 表示当前用户的主目录，例如 `deploy` 的 `~` 通常是 `/home/deploy`。
- Linux 路径区分大小写，`Site` 和 `site` 是两个名字。

### 关键目录

| 目录 | 用途 | 本课程中的例子 |
| --- | --- | --- |
| `/etc` | 系统与服务配置 | `/etc/nginx/`、`/etc/systemd/system/` |
| `/var/www` | 网站文件 | `/var/www/mysite/` |
| `/var/log` | 日志 | `/var/log/nginx/` |
| `/opt` | 自建应用或第三方应用 | `/opt/mock-api/` |
| `/home/deploy` | 普通用户个人文件 | 上传包、脚本、临时工作目录 |
| `/tmp` | 可随时清理的临时文件 | 临时下载或测试 |

不要把网站放在 `/root`。Nginx 通常以 `www-data` 用户读取文件，而其他用户无法穿过 `/root`，容易得到 403。

### 文件权限

```bash
ls -ld /var/www
namei -l /var/www/mysite/index.html
```

权限中的 `r`、`w`、`x` 分别表示读、写和执行；目录的 `x` 表示“可以进入/穿过”。排查 403 时，`namei -l` 能逐级显示路径权限。

不要用 `chmod -R 777` 解决权限问题。先明确谁需要读、谁需要写，再设置属主和最小权限。**【示例】** 网站目录存在后，如果静态文件由 `deploy` 发布、Nginx 只读，可以设置：

```bash
sudo chown -R deploy:www-data /var/www/mysite
sudo find /var/www/mysite -type d -exec chmod 755 {} \;
sudo find /var/www/mysite -type f -exec chmod 644 {} \;
```

两条 `find` 命令的结构：

- `chown -R deploy:www-data 路径`：递归（recursive）把路径内所有项目的所有者设为 `deploy`、所属组设为 `www-data`；
- `find /var/www/mysite`：从这个目录向下查找；
- `-type d` / `-type f`：只选择目录 / 只选择普通文件；
- `-exec ... {} \;`：对每个找到的项目执行一次命令；`{}` 会被替换为当前路径，`\;` 表示本次 `-exec` 结束；
- 目录用 `755`，使 Nginx 可以进入；普通静态文件用 `644`，使 Nginx 可以读取但不能修改。

`chown -R` 和两条 `find -exec` 都会递归修改大量项目，执行前先用不带 `-exec` 的 `find /var/www/mysite -type d` 或 `-type f` 预览目标。

## 0.3 更新系统与安装基础工具

**【必做】** `apt update` 更新软件目录，`apt upgrade` 才安装更新：

```bash
sudo apt update
sudo apt upgrade -y
sudo apt install -y curl nano rsync lsof dnsutils ufw
```

`apt update` 只刷新可安装软件清单；`apt upgrade` 根据清单升级已安装软件；`apt install` 安装指定软件包。`-y` 自动回答安装过程中的“是否继续”，因此执行前要先确认包名和升级范围。

**【可选】** 下面是后续可能用到的增强工具，不安装也不影响第 1 篇主线：

```bash
sudo apt install -y wget git vim tree unzip zip jq tmux
```

如果升级提示需要重启：

```bash
test -f /var/run/reboot-required && cat /var/run/reboot-required
```

`test -f 路径` 检查普通文件是否存在；只有检查成功时，`&&` 后的 `cat` 才会显示文件内容。没有任何输出通常表示系统没有创建“需要重启”标记。

**【可选・谨慎】** 只有前一条确认需要重启时再执行。重启会断开 SSH 并暂时中断网站，应选择合适时间：

```bash
sudo reboot
```

常用软件管理命令：

```bash
apt search nginx
apt show nginx
sudo apt install 软件包名
apt list --upgradable
```

## 0.4 文件、目录和文本操作

| 目的 | 命令示例 |
| --- | --- |
| 查看目录 | `ls -lah /var/www` |
| 切换目录 | `cd /etc/nginx`、`cd ..`、`cd ~` |
| 创建多级目录 | `sudo mkdir -p /var/www/mysite` |
| 复制文件/目录 | `cp file file.bak`、`cp -a site site.bak` |

| 分页查看 | `less /var/log/syslog`，按 `q` 退出 |
| 查看末尾 | `tail -n 50 app.log` |
| 实时追踪 | `tail -f app.log`，按 `Ctrl+C` 结束 |

```bash
sudo nano /etc/example.conf
```

```bash
pwd

```

## 0.5 上传静态网站文件

静态网站通常先在本机完成构建，再把 `dist/` 或 `build/` 内的成品上传到服务器。不要把 `node_modules/` 当网站成品上传。

### 【二选一】使用 scp

以下命令在自己的电脑执行：

先创建远端目录，再复制构建产物的内容：

```bash
ssh deploy@服务器公网IP "mkdir -p /home/deploy/site-upload"
scp -r ./dist/* deploy@服务器公网IP:/home/deploy/site-upload/
```

`scp` 通过 SSH 复制文件；`-r` 表示递归复制目录内容。冒号左边是远端登录目标，冒号右边是远端路径。

通配符通常不包含以点开头的文件；如果构建产物包含这类文件，优先使用下面的 rsync，或先打包再上传。上传后应确认 `index.html` 位于 `site-upload` 的第一层，而不是多套了一层 `dist/`。

### 【二选一・推荐】使用 rsync

macOS/Linux 或安装了 rsync 的环境可执行：

```bash
ssh deploy@服务器公网IP "mkdir -p /home/deploy/site-upload"
rsync -av --delete ./dist/ deploy@服务器公网IP:/home/deploy/site-upload/
```

命令拆解：

- `-a`：archive，递归同步并尽量保留时间等属性；
- `-v`：verbose，显示正在处理的文件；
- `--delete`：删除目标端多出来的文件，使目标与源保持一致；
- `./dist/` 末尾的 `/`：同步 `dist` 里面的内容；没有末尾 `/` 往往会在目标下再形成一层 `dist` 目录；
- `deploy@服务器公网IP:路径`：通过 SSH 同步到远端。

**【谨慎】** `--delete` 会删除目标中源目录已不存在的文件，第一次使用前先加 `--dry-run` 查看结果：

```bash
rsync -av --delete --dry-run ./dist/ deploy@服务器公网IP:/home/deploy/site-upload/
```

第 1 篇会把上传内容发布到 `/var/www/mysite/`，并介绍可回滚的目录结构。

## 0.6 进程、服务、端口和 HTTP

这是服务器部署最重要的一组关系：

```text
程序启动后成为进程
进程监听 IP:端口
客户端连接这个 IP:端口
systemd 负责启动、停止、重启和记录服务日志
```

例如：

- Nginx 监听 `0.0.0.0:80` 和 `0.0.0.0:443`，表示接受外部请求；
- 后台应用监听 `127.0.0.1:8080`，表示只允许服务器本机连接；
- Nginx 再把 `/api/` 请求转发到 8080。

常用命令：

```bash
ps aux | grep nginx
sudo ss -lntp
sudo lsof -iTCP:8080 -sTCP:LISTEN
systemctl status nginx --no-pager
journalctl -u nginx -n 50 --no-pager
curl -i http://127.0.0.1
```

其中几个不常见参数：

- `ps aux`：列出所有用户的进程及详细信息；配合 `grep nginx` 过滤名称，但结果通常也会包含 grep 自己；
- `ss -lntp`：`l` 只看监听、`n` 不把端口转换为服务名、`t` 只看 TCP、`p` 显示进程；查看其他用户进程通常需要 `sudo`；
- `lsof -iTCP:8080 -sTCP:LISTEN`：列出占用 TCP 8080 且处于监听状态的进程；
- `journalctl -u nginx -n 50 --no-pager`：`-u` 只看 nginx 单元，`-n 50` 取最后 50 行，`--no-pager` 直接输出后退出。

`curl` 常用参数：

| 参数 | 含义 |
| --- | --- |
| `-I` | 只获取响应头，适合检查状态码与重定向 |
| `-i` | 同时显示响应头和正文 |
| `-v` | 显示连接、TLS 和请求细节 |
| `-L` | 跟随 301/302/308 重定向 |

## 0.7 云安全组与 UFW

### 云安全组

在腾讯云控制台为实例配置入站规则。第一阶段只需要：

| 端口 | 来源建议 | 用途 |
| --- | --- | --- |
| TCP 22 | 优先限制为自己的公网 IP；否则暂用 `0.0.0.0/0` 并启用密钥登录 | SSH |
| TCP 80 | `0.0.0.0/0`、IPv6 场景再配置 `::/0` | HTTP 与证书验证 |
| TCP 443 | `0.0.0.0/0`、IPv6 场景再配置 `::/0` | HTTPS |

不要为后台应用开放 8080，也不要为数据库开放 3306、Redis 开放 6379。它们不是公网入口。

### 【推荐】UFW

启用 UFW 前先允许 SSH，否则可能把自己锁在服务器外：

```bash
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'
sudo ufw enable
sudo ufw status verbose
```

- `allow OpenSSH` 使用系统预置的 SSH 应用规则，通常开放 TCP 22；如果你修改过 SSH 端口，要先检查并调整；
- `allow 'Nginx Full'` 使用 Nginx 安装的应用规则，同时允许 HTTP 80 和 HTTPS 443；
- `enable` 真正启用 UFW，可能立即改变网络访问；
- `status verbose` 只读显示启用状态、默认策略和规则。

可以执行 `sudo ufw app info OpenSSH` 查看 SSH 规则；安装 Nginx 后，再用 `sudo ufw app info 'Nginx Full'` 查看 Nginx 规则实际包含哪些端口。

如果系统尚未安装 Nginx，就先只执行 `sudo ufw allow OpenSSH`，安装 Nginx 后再添加 `Nginx Full`。

启用 UFW 时，它应与云安全组保持相同的最小开放原则：公网网站只需 22、80、443。Docker 可能直接添加底层防火墙规则，因此不能只依赖 UFW 来保护错误发布的容器端口；容器端口还应显式绑定 `127.0.0.1`。

## 0.8 系统体检与日志

```bash
uptime                 # 运行时长和系统负载
free -h                # 内存
df -h                  # 文件系统空间
df -ih                 # inode 使用率
top                    # 进程资源占用，q 退出
systemctl --failed     # 启动失败的服务
journalctl -p err -b   # 本次开机以来的错误日志
```

**【验证结果】**

| 检查 | 主要看什么 | 需要关注的现象 |
| --- | --- | --- |
| `uptime` | `load average` 的 1、5、15 分钟平均负载 | 长期明显高于 CPU 逻辑核心数，需要找高负载进程；短时峰值不等于故障 |
| `free -h` | `available`，不是只看 `free` | `available` 长期很低且频繁使用 swap，可能内存不足 |
| `df -h` | 各文件系统 `Use%` | 接近 100% 会导致日志、更新和服务写入失败，应提前处理 |
| `df -ih` | inode 的 `IUse%` | inode 用尽时即使还有容量也不能创建新文件 |
| `systemctl --failed` | 失败单元列表 | 正常时没有失败单元，并显示 0 个 failed units |

负载和内存没有适合所有服务器的单一告警值，应结合 CPU 核数、业务基线和持续时间判断。

网站故障的固定排查顺序：

1. `systemctl status 服务名 --no-pager`：服务是否运行；
2. `journalctl -u 服务名 -n 100 --no-pager`：为什么失败；
3. `ss -lntp`：预期端口是否监听、监听在哪个地址；
4. `curl`：先测后台，再测 Nginx，再测公网域名；
5. 检查 UFW、安全组和 DNS。

不要只盯着浏览器的“打不开”。浏览器提示是链路最外层的结果，服务日志通常更接近原因。

## 0.9 读懂验证结果

### systemctl：当前状态与开机启动

**【验证】** 查看服务完整状态：

```bash
systemctl status nginx --no-pager -l
```

输出中最重要的是：

```text
Loaded: loaded (...; enabled; ...)
Active: active (running) since ...
Main PID: 1234 (nginx)
```

| 信息 | 含义 | 是否正常 |
| --- | --- | --- |
| `Active: active (running)` | 服务当前正在运行 | 长期运行的 Nginx、后台服务正常 |
| `Active: active (exited)` | 启动任务已成功结束，没有常驻主进程 | 对一次性初始化服务可能正常，要结合服务类型 |
| `Active: inactive (dead)` | 当前没有运行 | 若预期服务应在线，则异常 |
| `Active: failed` | 最近一次启动或运行失败 | 异常，立即查看状态底部和 journal 日志 |
| `Active: activating` | 正在启动 | 短时间正常；长期停留说明启动被卡住 |
| `Active: deactivating` | 正在停止 | 短时间正常；长期停留说明退出被卡住 |
| `Loaded: ... enabled` | 已设置随系统启动 | 不代表现在一定运行 |
| `Loaded: ... disabled` | 未设置随系统启动 | 服务可能仍然处于 running |
| `Loaded: ... masked` | 服务被禁止启动，手工 start 也会失败 | 除非明确设计如此，否则需要查明是谁屏蔽了服务 |
| `Main PID` | 主进程编号 | 排障时用于对应进程，但不需要记住数字 |

常见状态变更命令会修改服务，执行前先确认服务名和影响：

| 命令 | 当前是否改变 | 开机策略是否改变 |
| --- | --- | --- |
| `sudo systemctl start nginx` | 立即启动 | 不改变 |
| `sudo systemctl stop nginx` | 立即停止 | 不改变；如果仍为 enabled，下次开机还会启动 |
| `sudo systemctl restart nginx` | 停止后重新启动，可能短暂中断 | 不改变 |
| `sudo systemctl reload nginx` | 服务支持时平滑重载配置 | 不改变 |
| `sudo systemctl enable nginx` | 不会立即启动 | 改为开机启动 |
| `sudo systemctl enable --now nginx` | 立即启动 | 改为开机启动 |
| `sudo systemctl disable nginx` | 不会立即停止 | 取消开机启动 |
| `sudo systemctl disable --now nginx` | 立即停止 | 取消开机启动 |

并非所有服务都支持 `reload`。Nginx 支持，其他服务应先看它的文档或 `systemctl status`。

也可以只获得机器易读的结论：

```bash
systemctl is-active nginx
systemctl is-enabled nginx
```

正常的长期服务通常分别输出 `active` 和 `enabled`。命令没有输出预期值时继续执行：

```bash
journalctl -u nginx -n 100 --no-pager
```

最后几十行中的红色或 `error` 只是线索，还要结合时间、服务名和第一条根因信息判断。反复出现的后续错误不一定是根因。

`failed` 状态中常见线索：

| 提示 | 常见方向 |
| --- | --- |
| `Unit ... could not be found` | 服务未安装或服务名写错 |
| `status=1/FAILURE` | 程序自己以非 0 状态退出，需要看它前面的应用错误 |
| `status=203/EXEC` | `ExecStart` 路径错误、文件不存在或不可执行 |
| `status=200/CHDIR` | `WorkingDirectory` 不存在或无权进入 |
| `status=217/USER` | `User`/`Group` 不存在或无法切换 |
| `activating (auto-restart)` 反复出现 | 程序启动即退出，systemd 正按重启策略循环拉起 |

这些数字只是定位方向，最终原因仍以该服务同一时间段的完整日志为准。

### ss：谁在监听端口

**【验证】**

```bash
sudo ss -lntp
```

重点看 `State`、`Local Address:Port` 和 `Process`：

| 示例 | 含义 |
| --- | --- |
| `LISTEN ... 0.0.0.0:80 ... nginx` | Nginx 接受所有 IPv4 网卡上的 80 请求 |
| `LISTEN ... [::]:443 ... nginx` | Nginx 接受 IPv6 443 请求；部分系统也可能同时覆盖 IPv4 |
| `LISTEN ... 127.0.0.1:8080 ... python3` | 后台只允许本机访问，符合本课程目标 |
| `LISTEN ... 0.0.0.0:8080 ...` | 后台监听所有 IPv4 网卡，应检查是否意外暴露 |

没有目标端口，通常说明服务未启动、启动失败或监听了其他端口。

### curl：HTTP 是否正常

**【验证】** 只输出状态码：

```bash
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1/
```

这里 `-s` 关闭进度条，`-S` 保留错误信息，`-o /dev/null` 丢弃响应正文，`-w` 按指定格式额外输出结果；`%{http_code}` 是 curl 提供的 HTTP 状态码变量，`\n` 表示换行。

| 状态码 | 主要含义 |
| --- | --- |
| `200` | 请求成功 |
| `301` / `308` | 重定向；HTTP 跳转 HTTPS 时属于预期 |
| `403` | Nginx 找到了站点，但权限或访问规则拒绝 |
| `404` | 请求已到达服务，但路径/文件不存在 |
| `502` | Nginx 无法连接后台或收到无效响应 |
| `504` | Nginx 等待后台响应超时 |
| `000` | curl 没有收到 HTTP 响应，常见于连接、DNS 或 TLS 失败 |

使用 `curl -I` 时还应查看第一行和 `Location`：

```text
HTTP/1.1 301 Moved Permanently
Location: https://example.com/
```

这表示 HTTP 跳转到 HTTPS 正常，不是网站故障。

### UFW 与 Nginx 配置

**【验证】**

```bash
sudo ufw status verbose
sudo nginx -t
```

- UFW 输出 `Status: active` 表示主机防火墙已启用；还要继续核对规则是否包含 SSH 和 Nginx。
- `Status: inactive` 表示 UFW 没启用，不代表云安全组也没启用。
- Nginx 验证必须同时看到 `syntax is ok` 和 `test is successful` 才算通过。
- `nginx -t` 失败时不要 reload；输出通常会指出出错文件和行号。
